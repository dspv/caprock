# Caprock — UI

The screens and the visual direction. Every screen answers "what's happening / what does it cost / where do I need to act" ([01-product.md § Product principles](01-product.md#product-principles)). Data comes from the API in [03-contracts.md](03-contracts.md); which screen ships in which phase is in [09-execution-plan.md](09-execution-plan.md).

## Now (default, "the useful waiting screen")

The screen you leave open while Claude works. In the desktop app's Dashboard
tab (`NowScreen inApp`) it keeps its figures — Today, plan limits, the pulse,
all time, at a glance, the activity feed, full width — and hides the session
cards, their *show ended* row and the Projects panel: the sidebar beside it
lists the same projects and sessions, and the first tester found the two
"90% the same" (2026-10-09, translated). Hidden, not removed: the browser and
the phone show everything below. Per agent card:

- **Human-readable narration** of current activity ("editing `auth/middleware.go`", "running tests — 2nd attempt"), derived from tool events, not raw logs. The tool-event → human-phrase map is unit-tested (T7).
- **Plan progress** — parsed from TodoWrite/task-list tool events when present; else "N tool calls, M files touched".
- **Live burn**: tokens + $ this task, session context fill %, time since last event.
- **Health badges**: `working / idle / waiting-on-you / looping? / error`.
- One-click actions: open detail, send message, pause/kill.
- **Loop detector**: same tool + similar input ≥ K times in T minutes → banner + optional auto-pause. This is the "session in a loop drains your budget" killer feature. Defaults and rule: [02-architecture.md § Loop detector](02-architecture.md#loop-detector).

At the top of Now, an **attention** strip reports only what deserves interrupting someone: a live loop (with the evidence and what that session has spent so far — read-only tools are excluded, see below), a session that hit an error, and a session that has been waiting for you long enough to be costing you time (default 15 minutes — a question asked two minutes ago is not a problem). **That row carries no detail line**, unlike the others: they show the activity phrase because it is the evidence — an error's phrase names what broke — while a waiting session's phrase is the fixed string "waiting for you", so the row read `Waiting on you · caprock · waiting for you`, the same sentence twice in two prepositions with the repeat greyed as though it were adding something. The title says it once, and "what did it ask?" beside it is the part that tells you anything. Cost alone is never a rule: spending is the job. **A "many turns, almost no files touched" rule was removed** — `files_touched` counts only Edit/Write/MultiEdit/NotebookEdit, so every file changed through Bash (`sed -i`, a heredoc, a python one-liner) was invisible to it, and an agent under bypassed permissions is told to prefer exactly those. On the owner's machine it had fired three times ever, on sessions making 636, 418 and 288 Bash calls: all three false, one of them shipping three releases while the banner read "no files touched". It had already been reworded once when the owner could not judge his own flagged session, which was the first sign; a rule whose own comment concedes the product cannot tell investigation from waste is arguing not to interrupt anyone. Counting files out of Bash command text would be guesswork about shell syntax ([rule 6](../CLAUDE.md) prefers no number to an invented one); if it returns it should be built on `internal/gitdiff`, which already knows what a session really changed. Each row carries the measured fact behind it, a one-click way into the session, and a cost — **labelled `session total`, because that is what it is**. The figure is the session's whole spend, and bare beside "Stuck in a loop" it read as the price of the repetition: a $58.85 the loop had not cost. Charging the loop's own window instead does not fix it — measured on a real two-hour loop, its window held $47 of which essentially all was the useful work happening alongside it, so that number would be wrong too and harder to argue with (rule 6). The honest move is to keep the number what it is and say so in the open rather than only on hover. **The premium hint beside the loop row states what a cap would actually do**: the cap pauses only sessions Caprock started ([rule 7](../CLAUDE.md)), and 122 of the 127 sessions that did real work on the owner's machine were started by hand — so "a cap that stops this" was, nearly every time it appeared, an offer to stop something the cap cannot reach. On a session Caprock does not own it reads "a cap covers sessions Caprock starts" and offers "what a cap does" instead; unknown ownership is treated as not owned, because a promise made on a guess is the thing being fixed. **There is no "all clear" state**: the strip renders nothing when nothing is wrong, because an always-on banner trains people to stop reading the space where the real warning will appear. That leaves one genuine gap — a quiet dashboard and a dead one look identical, since nothing moves in either — and it is answered by the header's connection state (`ConnectionState`, WP-13): `Live` only while something came from the daemon in the last 24 s (its pings arrive every 10), otherwise `Not answering — reconnecting`, `Catching up…`, `Reconnecting (n) · next try in s` or `Offline since hh:mm`. Liveness is a fact about the connection; "all clear" would be a verdict about the machine, and only the first is ours to state. It re-renders on a one-second tick rather than only when a frame arrives: on an idle machine no frame arrives *by definition*, so the old dot froze at `live · now` and kept claiming it for hours, and it said `live` for as long as the socket object was open, which a phone whose network dropped silently kept for minutes — a stale liveness indicator being worse than none, because it is the one people trust. Being expensive is never on its own a reason to fire — spending is the job. Rules are pure and unit-tested in `ui/src/lib/attention.ts`.

Beside the Projects roll-up sits **Live activity** — one column of what every session on the machine is doing, newest first, fed by the same `/v1/live` WebSocket and seeded from recent history so it is never empty on open. Each line is a short past-tense phrase with the repo, an optional monospace detail (a file name, a shortened command), and how long ago it happened; a click opens that session. Only events a human would want to read become lines — successful tool results, assistant turns, cost ticks and mail are dropped, because a feed of raw event kinds is noise and noise is what makes people stop looking. Absolute paths in shell commands collapse to their last two segments so the verb stays visible. A pause control freezes the stream for reading. Phrasing lives in `ui/src/lib/feed.ts` and is unit-tested.

**Panels refetch on live frames, never on top of themselves.** Every panel asks again when a frame arrives (at most every 400ms) and on its own interval; a refetch asked for while the last is still running is sent once, when it lands (`ui/src/lib/useApi.ts`). Without that, a busy session on a large database stacked dozens of the same seconds-long aggregate in the daemon: measured 2026-09-30 on a copy of the owner's database with one tab open, today's summary took 11s and rising to 22s, against 2-5s with the guard.

Below the cards, a **Projects** roll-up answers the question a session list cannot: what each repo costs and who is working in it. One row per project with its measured spend, token total, session count, a **sparkline** of when that spend happened, and a green dot when a session is live in that repo. The range selector (`today` / `7d` / `30d` / `all`) defaults to **30d** — "today" is empty most mornings, and an empty panel on first open reads as a broken feature rather than an honest zero. Data comes from `projects` in `/v1/stats/summary` ([03-contracts.md](03-contracts.md)); every figure is measured at API list price, never modelled.

**Both figures are always shown**, and both are legible: tokens lead the row (17px accent) with cost directly beneath at reading size (13px `text-fg-muted`, the tone used for text meant to be read — `text-fg-faint` is reserved for chrome). Tokens lead because on a flat plan the dollar figure is not money owed but a proxy for consumption, and because the panel header already carries the dollar total. The header states both in the same relationship (`10.00M · $1,000.00 total`), and an expanded directory row states both on one line. There is no control for choosing between them: a toggle would make the reader re-decide which half to see on every visit, and the row has room for two numbers. The sparkline, the shared ceiling and the fallback share bar are all scaled on **tokens**, matching the figure that leads the row — a picture scaled on cost under a tokens headline would be a second, silently different ranking, and the two orderings genuinely differ because a cheap model burns tokens cheaply. Both series still travel in the payload (`spark.cost` and `spark.tokens`); the client simply plots one.

Each repository row **expands into its directories**, and the breakdown is charged by **which files Claude touched** — not by the directory a session was launched from. Nobody opens a terminal in `/services/api` to work on it; they open the repository root and let Claude edit across services, so the old cwd-keyed rows answered "where was the terminal" and only one repository on the owner's machine expanded at all. Rows read as paths from the root (`/`, `/services/api`), sorted by cost.

The breakdown is a **tree, one level at a time**. It was a flat list of full paths: **43 rows** at depths 0 to 4 on the owner's `caprock` — `/ui/src/components`, `/ui/src/screens`, `/ui/src/lib`, `/ui/src`, `/internal/store`, `/.ai`, `/` — with nothing on screen saying the first three live inside `/ui`. Sorted by cost it answered "what is most expensive"; it could not answer "what does `/ui` cost", which is the question a monorepo asks, and at 43 rows the eye found neither. Expanding now shows the **9 rows** directly under the root, each carrying its subtree's total; each expands again, to a cap of **three levels** — `/ui/src/screens` is the deepest row reachable.

- **The cap is a display choice, so the tree is built in the client** (`ui/src/lib/pathtree.ts`) from the flat list the daemon already sends. The payload carries cost, tokens and turns per path, so the tree is arithmetic over data already on the wire; putting the cap in the API would make every future consumer inherit one panel's layout budget and would turn a stylesheet-sized decision into a contract change. The flat list stays the single truth, so the two can never disagree.
- **Spend deeper than the cap is charged to the deepest visible row, and the row says so** — `+1 deeper` beside the path, with the count on hover. It cannot be dropped (the parts would stop summing to the whole) and it cannot have a row (that is what the cap means), so the only honest option left is to absorb it visibly. A number that quietly swallows its children is exactly what rule 6 exists to prevent.
- **A parent's own spend is stated apart from the roll-up.** The row's figures are the **subtree** — `/ui` reads $390.74, everything at or below it — and when work touched a file directly in `/ui` a sub-line says `$0.39 here · $390.35 in 1 subdirectory`. Without it a reader cannot tell "this directory cost X" from "this subtree cost X", which are the same number only on a leaf.
- **A pass-through directory collapses into its child** — `/ui/src/lib` and `/ui/src/components` under a `/ui/src` that has no spend of its own show as one `/ui/src` row, not two clicks. The collapse is **conditional**: a directory with spend of its own never merges, because that would move real money into a directory the work did not happen in.
- **The repository root is not a row of the tree.** Every path is under `/`, so a tree rooted there would put one click between the reader and everything they came for, on every repository. Its children are the first level, and the root's own spend (`README.md`, `Makefile`) becomes a leaf row beside them, still written `/`.

**Nothing in the breakdown navigates.** A row is a figure, not a link — the only interactive thing is its expander, which is the same chevron the repository row uses. The rows were never links, but expanding a repository injected dozens of them, grew the panel far past the **Live activity** feed beside it, and the next click landed on a feed row — every one of which *is* a link to a session. The owner clicked a directory and arrived at a session in a **different repository**, unable to tell what he was looking at. A click that lands a user somewhere they cannot orient is worse than a row that does nothing, so the fix is both halves: fewer rows to scan, and rows that are inert and look inert.

Attribution **carries forward**: a turn counts toward the directory of the **most recent file it touched**, and keeps counting there until it touches a file somewhere else. Work happens in stretches — after "finish /app" Claude edits, runs the tests, reads the output, greps, edits again — so the commands, tests and searches between two edits count toward the directory being worked on. Reading, editing or writing a file counts as touching it; running a command does not. Each turn's cost goes **whole** to one row, never split between two — a split would need a model of how much of a turn each file deserved, and no such measurement exists — so the parts still sum exactly to the repository total (rule 6). The rule is stated on hover, because this is a **stated rule, not measured file-by-file attribution**, and the difference is the whole of its honesty.

This **replaced a strict rule** that charged a directory only when every file a turn touched was in it. That rule was exact and useless: it counted only the minutes containing a direct file edit and discarded the hour of commands around them, putting **87.6%** of the owner's monorepo into "repository-wide work". The user asked what a service cost and seven eighths of the answer was "we could not tell". Under carry-forward the same repository reads `/app` **61.0% ($2090.67)**, `/.ai` 6.8%, `/app/tests` 2.8% (measured 2026-08-22, all time).

**Two rows are not directories.** They sit under a small-caps `not a directory` heading and each carries its own explanation on hover. They used to render in **italic**, which separated them from the table by making them look like a different product — a slanted face the panel has nowhere else reads as an error state or as pasted-in text, not as a row of the same table. They are siblings of the directory rows: their spend is real and part of the repository total. So they now read as table rows — same 12px, same tone, same alignment, same right-edge numerals — and are separated by **role** instead: the heading says what they are once, and the path column drops its **monospace**, which is the difference that is actually true (`mono` in this panel means "a literal string from the machine"). Neither is called "unattributed": that word describes caprock's bookkeeping rather than the user's work, and reads as "the tool failed to figure this out".

- **`outside the repository`** — the larger of the two, **25.8%** of the owner's monorepo and **28.7%** of `caprock` (measured 2026-08-22). This is not other people's work: it is work on *this* project whose files live elsewhere — Claude's notes under `~/.claude/projects/<project>/memory`, agent scratchpads under the per-session temp directory, the e2e run's output directory, occasionally another checkout. It counts toward the repository total but is charged to no directory inside it, because folding it into the root would claim work happened in the checkout that did not.
- **`repository-wide work`** — now small and narrow: a session's **opening turns, before Claude had touched any file**, so there is no directory yet for them to count toward ($2.39 of $3426 in the monorepo). It is usually absent entirely; a bucket row that cost $0 is omitted rather than rendered as a puzzling `$0.00`.

Each directory row states **tokens, its share, and cost** — all three for the **subtree**. The share is a percentage of the **repository total including both non-directory rows**, so the column sums to 100% and the part that belongs to no one directory is visible as its own number instead of inflating the directories that could; the breakdown header says this in words, because a percentage whose base the reader has to guess is exactly what rule 6 exists to prevent. It is a share of **tokens** and sits beside the token figure rather than between the two numbers, where it would read as qualifying both; the cost share is on hover, since two competing percentages side by side would reintroduce the ambiguity. A subtree's share is **summed from the shares the daemon sent**, never recomputed: the server divides by a total the panel does not have, and recomputing would silently substitute a different base for a percentage the contract describes. Percentages **floor** (`fmtPct`) — 99.6% is 99%, and nothing reads as 100% until it is — with one exception: a row with real spend whose share floors to zero shows `<0.1%`, because a bare "0%" beside a non-zero dollar figure states two contradictory things about the same money.

The sparkline **replaced** a share-of-the-largest bar, which restated the ranking the sorted numbers already gave — the widest bar sat on the top row by construction — and so spent the row's only free horizontal space on information the reader had. When the spend happened is in no number on the row: $40 in one afternoon and $40 across three weeks are the same row until you draw them. One column per bucket, following the range (`30d` → 30 days, `7d` → 7, `today` → 24 hours), so the picture and the number beside it always describe the same period. Every row is scaled to one shared ceiling, so heights are comparable between rows; an empty bucket is drawn as a hairline rather than left blank, the way the live pulse draws a silent minute, because a gap reads as a rendering fault while a flat floor reads as silence. `range=all` sends no series and the row keeps the share bar. Model in `ui/src/lib/spark.ts`, unit-tested and kept separate from the canvas that paints it.

### A card says what its session was about

Every card carries one line under its header naming what the session was
about (FB-035): the agent's own title — Claude Code's `ai-title`, the name its
own `/resume` picker shows, or Codex's or OpenCode's thread name — in the
foreground colour, or else the first
prompt that says something, muted and in quotation marks, because it is a
quotation rather than a name. Without it a list of ended sessions was a list of
identical rows: the same project, a short id, and "ended". Sessions with
neither (a `say ok` probe, a `/clear` and nothing after) show no line rather
than a guess. The rule for which prompt counts lives in
[03-contracts.md](03-contracts.md).

### Ended cards, and finding one

An ended card says **worked**, with the span it was worked in and how long ago
— "29 Sep 14:02–16:40 · 17h ago" — not the last narrated state, which read
"waiting at the prompt" on a session that stopped weeks earlier, and not when it
was closed: after a reboot every card read the reboot's time (FB-037). The close
time is on hover. It carries **continue**, or a muted **can't continue**
with the reason on hover (see § Continue, and why not). With "show ended
sessions" ticked, a search box finds a session by what it was about, any prompt
typed in it, its project or branch (searched on the server, so every session
counts, not only the loaded page), and **show N more** pages past the first
200.

### Interrupted by a restart

When Caprock (or the machine) last stopped with sessions running and they were
gone when it came back, a banner at the top of Now says so — "2 sessions were
still running when Caprock last stopped · 13h ago" — and lists each by project
and description with **continue** (FB-038). It is dismissed per stop, in the
browser, and a session drops out once continued. Checked on a copy of the
owner's database with a simulated stop: it named exactly the two sessions closed
at that moment and none of the live ones.

### One card per conversation

`/clear` and a fork each start a new session id, so one conversation in one
terminal became a row of cards (FB-039: "four sessions on one repo, and I open
two at most"). An ended session another listed session continues is folded into
that one, which says "continues N earlier sessions" with each earlier part as a
link. The link is recorded, never guessed (see `parent_session` in
[03-contracts.md](03-contracts.md)).

## The agent switch

`all / claude / opencode / gemini / codex / deepseek`, in the middle of the Today
header, showing only the agents this machine runs, when it runs more than one. It applies to the whole screen — today's totals, the live pulse, the
activity feed, the projects list and the session cards — because a filtered
list beside an unfiltered total is how a reader ends up quoting a number that
means something other than what the heading says.

Three decisions worth keeping:

- **OpenCode, Codex and DeepSeek Harness appear when the daemon reports it is
  reading them; Gemini when a Gemini session is in the list.** Neither the
  session list nor a day's summary can answer the first on their own: the
  screen fetches only live sessions unless "show ended" is ticked, and a
  machine's OpenCode or Codex history is usually all ended and older than
  today — so both are legitimately empty on exactly the machines that need the
  control. Gemini is judged by its sessions instead, because the `gemini`
  binary on PATH says nothing about whether any Gemini session exists.
- **`all`, not `both`.** Written when there were two agents, on the reasoning
  that a third would make `both` a lie — and then Gemini arrived and it would
  have. It is the part of this control a reader sees every time.
- **The selection is a filled pill, at 12px.** At 11px in a bordered strip the
  active state was a slightly lighter grey cell, and a control whose state has
  to be squinted at is one people misread — this one changes what every figure
  on the screen means.

Rows from an agent other than Claude Code carry a small mark — `oc` for
OpenCode, `gem` for Gemini, `cdx` for Codex, `dsh` for DeepSeek Harness. Only
those: on most machines every row is Claude
Code, so marking those too would put a badge on every line, and the mark exists
to answer "why is this one different". A project worked on with more than one
carries no mark, because claiming any one of them would be
wrong.

## At a glance

A collapsible block on Now, after All time, that draws the all-time figures
as three donuts and an agents row (`ui/src/components/AtAGlance.tsx`, data
from `/v1/history?range=all` and `GET /v1/glance`):

- **Where the money went** — cost by model, the top four by name and the rest
  as "other"; the centre is the leader's share.
- **The bill by token type** — input, output, cache write and cache read, each
  priced at the model's current list price. The centre is the cache-read
  share, labelled as re-reading context: the same figure the context tax line
  gives in dollars, drawn as the part of the bill it is.
- **Most-used tools** — calls by tool, top five and "other".
- **Agents** — one tile per agent with its character (the Week card's),
  turns, cost and a ring of its share of all-time cost. Claude Code's
  subagents get their own tile ("1,647 subagents"), because on the owner's
  machine they were 13% of the cost and a different kind of work. The ring is
  labelled **of spend** beside it, with a tooltip giving both figures ("81%
  of all-time spend across every agent — $12,250 of $15,043"): the owner
  read a bare "81%" and could not tell of what (2026-10-04). Tiles are at
  reading size — a 48 px character, 14 px name, 12.5 px figures — and at
  phone width the cost wraps under the turns instead of running into the
  ring.

A **Charts | Numbers** switch in the header turns every donut into a table of
the same rows, for reading exact figures and for screen readers (each donut
also carries an `aria-label` listing its segments). The open/closed state and
the view are remembered per browser (`caprock-glance-open`,
`caprock-glance-view`; storage failures fall back to open charts). The SVG is
drawn by hand — no chart library — and the donuts stack at phone width.

## Hooks banner

Shown on Now when Claude Code's settings file lacks some of Caprock's hook
events (`/v1/status.hooks.missing`). One line says what it means — activity
still arrives from transcripts, a few seconds late; hooks make it live — and
**Install hooks** fixes it: `POST /v1/hooks/install` runs the code behind
`caprock hooks install` and the banner reports what the file holds
afterwards. On success it reads "Hooks installed ✓": sessions started from
now on report live, including resumed ones, and a session already running
keeps the hooks it started with until it is restarted — Claude Code loads
hooks when a session starts. The command stays as a secondary "or run in a
terminal" line, and the banner names the settings file it checked, so a
preview daemon with a temporary HOME is obvious. Dismissing it (×) is
remembered per browser, keyed on the exact missing set
(`caprock-hooks-banner-dismissed`), so it returns only when that set changes.

## Live pulse

One track per session on Now, one bar per minute of the last hour. The bar's height is how much happened in that minute and its colour is what it cost — green a cheap minute, amber typical, bright an expensive one — so the shape of a track is the shape of the work: a task that ramped and finished draws a bell, steady grinding a plateau, working in bursts a comb. Nothing is decorative; there is no motion that does not correspond to a recorded event.

The state on the right comes from the daemon's narrator, not from the bars. The bars describe the past hour; health describes this moment, and they answer different questions — a track that reads "working" while Claude sits waiting for you to type is worse than one that says nothing. A high repeat count still wins over health, because it is the one thing the bars know that health does not.

Clicking a minute opens the session **at that minute** — the timeline scrolls to those events and marks them with an accent rule. Landing at the top of a thousand-event session with no indication of what you clicked is the same as not having clicked. The route carries the instant (`#/session/{id}?at=<unix-ms>`), so the position is shareable and survives a reload.

Hovering a track names the minute under the pointer and what happened in it — event count, model turns, cost — including "nothing" for a silent minute, since "was anything happening here?" is a real question about a flat stretch.

Under the cost, a session row says **what state it is in and who is
working**: the state as a small coloured pill (working green, waiting or
repeating amber, error red, idle neutral), then the session's character with
a crowd beside it when subagents are live, the count in words ("4 agents" —
main thread plus each live subagent) and the model's display name ("Opus
5.5") at normal contrast. The first version drew 15 px icons, a faint "×4"
and a grey model, and the owner could not read it (2026-10-04). At phone
width the model gives way, and the chart takes its own line under the row
rather than shrinking to a sliver between the name and the agents. Live
subagents are the daemon's `live_subagents` (see
[03-contracts.md](03-contracts.md#at-a-glance-get-v1glance)).

**A row opens in place.** Clicking it (or its chevron) expands the project
under it rather than navigating: today's cost, tokens and sessions for the
project (from `/v1/stats/summary?range=today`, matched on the project's
directory), every live session in it — agent, model, state pill, live
subagents, what it is doing now and how long ago — each with a link to its
page, and the ways in: the project's terminal button (the same one as on the
Projects panel), **Open repo** and the latest pull request (the session
page's buttons, from its detail), and **Open session**. Which rows are open is
remembered per browser (`caprock-pulse-open`, by session id). Clicking a
minute on the chart still opens the session at that minute.

On the right, **×N same call** counts the most-repeated identical tool call within six minutes, using the same signature as the loop detector. It is worded as the measurement rather than a verdict, because polling a file with repeated Reads looks exactly like being stuck and only the person working knows which it was. Placeholder calls (`Bash true` and its cousins) are dropped outright — an agent makes them by the hundred and counting them reported every session as looping.

Colour encoded turns-vs-tool-calls first, and that was meaningless: the ratio sits near 1:2 almost every minute, so two near-identical minutes came out different colours and the legend explained a distinction nobody could see. Cost per minute varies eight-fold across an hour on a real session, which is worth noticing. A minute with no events draws a hairline rather than nothing, because a gap in a bar chart reads as a rendering fault while a flat floor reads as silence — and the legend shows the colours as chips rather than naming them in prose.

**The canvas repaints only when the data changes, never on a timer.** The first version ran a `requestAnimationFrame` loop that repainted every frame and visibly shimmered; a dashboard that flickers while you read it is worse than a still one.

The model (`ui/src/lib/pulse.ts`) is pure and unit-tested apart from the drawing, so a wrong bar can be told from a wrong pixel.

## What did it ask?

**A session at a permission dialog says so** ([ADR-036](08-decisions.md)): the stored `permission.prompt` makes the card and the session page read *waiting for approval — running `go test …`* (the call it asks about; *waiting for your answer* for `AskUserQuestion`) with the *waiting on you* badge, for every session, not only Caprock's own. Before, a session stuck at a dialog looked busy, since "waiting" meant only "the last event was `Stop`". The timeline shows the event as *waiting for approval: Bash* and the activity feed as *waiting for your approval*.

A session waiting on you is the one case where the terminal holds something the dashboard does not — except it does not: every assistant turn is already stored. A **what did it ask?** button appears on a waiting session's card and on its attention row, and opens the last thing Claude said.

It shows the last *complete* thought rather than the newest text. Roughly a third of sessions end mid-sentence ("Let me check that…"), and presenting that as the answer would send the reader to the terminal anyway — which is the trip this exists to save. When a newer line was skipped for that reason, the panel says so.

It shows and does not act. Typing into a session Caprock did not spawn is refused by rule 7, and that rule is worth more than the convenience: writing blind into a terminal interrupts work you cannot see. Reading carries no such cost, so this works for every session — including the ones started by hand, which is nearly all of them. The footer names where the reply goes instead of offering a box that would fail.

## Memory — does the handoff help?

With **Measure whether it helps** ticked under Settings → Memory between
sessions → Experiments (it holds the handoff back from one new session in
four), the Memory screen
opens with the comparison: median minutes and tool calls to a session's first
edit, with the handoff and without. Until each group has 5 sessions that
reached an edit it says how far the count has got instead of a number that
would swing with the next session.

## Memory — paging and the link back

The list pages backwards on demand (`load older answers`) rather than loading a fixed window. The fixed window looked like data loss: on a busy machine 500 notes is half a day, so the list jumped from "22h ago" to "30d ago" with nothing between, and the first outside user reasonably read the gap as missing history. Nothing was missing — the middle had never been fetched. `GET /v1/notes` takes `before=<event_id>` for this.

Each answer links to **the moment it was written** (`#/session/{id}?at=…`), not to the top of the session. The same reporter said the answers "did not feel connected to the session", which was exactly right: opening a thousand-event timeline at the beginning and leaving someone to find the passage they just clicked is the same as not linking at all.

## Feedback

A **feedback** button in the header, on every screen. Pick what kind of thing it is (broken / missing / unclear), type a sentence, press the button — two clicks and a few words is the whole interaction.

**Nothing is transmitted.** The dashboard composes a prefilled GitHub issue URL and opens it in a new tab; the user reads it, edits it, and submits it themselves. That is what makes this compatible with the promise the product is bought on, and the panel says so rather than leaving anyone to wonder.

The context a maintainer would otherwise have to ask for is gathered and **shown before anything happens**: version, platform, which screen, how many events, whether hooks and orchestration are on. Deliberately absent are project names, file paths and cost — those are the user's repositories and the user's money, and neither helps fix a crooked button. The data directory is left out for the same reason: it contains their username.

There is no rewriting of what the user typed. Turning "button is crooked" into prose needs a model, and Caprock makes no API calls; adding one would mean asking for a key or posting their words to a server. Structure does the same job — a chosen kind, their words verbatim, a context block underneath — and the title (`[bug] Lifetime: …`) makes the list scannable.

Long reports are clipped at 6,000 characters with a visible marker, because GitHub silently truncates a prefilled issue past roughly 8k and losing the end of someone's report without telling them is worse than asking them to trim it.

  Every file expands on its own (`components/DiffFiles.tsx`). Built for a

### Continue, and why not

The session header offers **continue here** for an ended session and **branch
here** for one running somewhere else, or — when neither can work — says why in
place of the button: the transcript is gone (Claude Code deletes them after 30
days by default), the folder it ran in no longer exists, Caprock cannot find
`claude` to start it, or the agent is not one Caprock can resume. Codex and
OpenCode sessions get **continue here** once ended (by their own id, see
[ADR-031](08-decisions.md)) and their own **copy command** either way; a Codex
or OpenCode session Caprock started that was never typed into says there is
nothing to continue. The server decides, from what is on disk
([03-contracts.md](03-contracts.md)); the header used to decide from who started
the session and which agent it was. Measured on a copy of the owner's
database on 2026-09-29, over its 116 ended Claude Code sessions: the 96 started
elsewhere all offered the button and 65 of those failed — 44 transcripts
deleted, 21 folders gone, each a terminal that opened and died — while the 20
Caprock had started offered nothing, though 12 of them could be resumed
(FB-036). The Terminal tab of an ended session
says it has ended and offers the same continue, rather than the copy written
for a live session somebody else started.

**A continue keeps the session's permission mode.** The owner runs Claude Code
with permissions skipped; a session he continued from Caprock came back in the
default mode and asked before every command (2026-10-06), because the resume
named no mode. The daemon now fills one in when the request has none
(`resume.permission_mode`, [03-contracts.md](03-contracts.md)): the mode the
session's own hooks last reported, else the Settings preference below. Beside
**continue here**, **branch here** and **Continue it here** a small select
shows that mode in the dialog's words (*Bypass · never asks*) and can change it
before the click; *default mode* is offered only when nothing was recorded. A
card on Now, with no room for a select, names it after the button (*bypass
permissions*), and the project terminal's **⋯** menu names it beside each
continue or branch. The trust prompt is unaffected: Caprock pre-accepts the
folder for every Claude Code launch, and `--permission-mode
bypassPermissions` (like `--dangerously-skip-permissions`) never suppressed it.

***Bypass · never asks* now never asks.** It is started as
`--dangerously-skip-permissions`, the flag the orchestrator's own unattended
workers use; `--permission-mode bypassPermissions` leaves the session
interactive, and the owner picked bypass for an autonomous run and was asked on
nearly every call (2026-10-07). Sessions are also started with `--add-dir` for
the directories Caprock writes to itself, so a pasted screenshot is not a
question. What neither can lift is Claude Code's own
`permissions.blockReadsOutsideWorkingDirectories`, a perimeter that asks in
every mode and on every command whose paths are computed at run time; a user
who wants an unattended run turns that setting off. See
[03-contracts.md](03-contracts.md).

**A session that exits leaves a shell, not a dead tab.** `/exit` — or `exit`,
or a crash — used to leave the tab showing a terminal nothing was behind: the
pty's exit frame reached the terminal client and no component listened. The
tab now becomes a shell in the session's own folder, keeping its place in the
strip and in a split (`replace-session`, `ui/src/lib/tabs.ts`); a shell that
exits is closed, since there is nothing to put in its place. Each window
showing the tab asks for that shell with `replaces: <session>`, so the app, a
browser tab and a phone get one shell between them, not one each.

**A restart of Caprock does not end a session it started** — the terminal lives
in a pty-host and the next daemon reattaches it, so the Terminal tab simply
shows it running ([ADR-033](08-decisions.md#adr-033--an-owned-session-outlives-the-daemon-its-terminal-lives-in-a-pty-host)).
What is left is a session started by a release from before that, or one whose
holder died (`detached`). Its Terminal tab says, in these words: *"This
session's terminal was closed when Caprock restarted. The conversation is saved
— Continue it here resumes it in a new terminal."* **Continue it here** is the
primary button: the same conversation under the same id, after the daemon stops
the terminal-less process (it is Caprock's own). Below it, **open a copy
instead** starts a fork and says that it leaves the old process running; **copy
command** stays. The header offers **continue here** for it too, not **branch
here**. The panel used to say *"Caprock restarted since this session began, and
its terminal went with that run"* over **branch here**, and the owner could not
tell what had happened or what the button would do (FB-040 before that: it
opened an empty terminal).

### Continue in another agent (relay)

**Continue in… ▾** sits beside continue/branch in the session header and lists
the agents this machine can start (`ui/src/components/RelayDialog.tsx`). It
answers the same wish as continue when continue cannot work — the transcript
gone, an agent Caprock does not resume — or when the work should move to
another agent. Choosing one opens a dialog whose first sentence says this
starts a **new** session with a summary as its first message, not the same
conversation, and that the agent sees only what is in the box. Below: the
folder, the passage's age, the changed-file and PR counts, and the brief
itself in an editable box (`GET /v1/sessions/{id}/relay`). Nothing is sent
until **Start <agent> with this message**; the new session opens on its
terminal. A folder that no longer exists disables the button and says why.
Both pages name the other end: "Carries on from a <agent> session: <title> —
started with a summary, not its conversation" and "Carried on in <agent>
<id>" ([ADR-032](08-decisions.md)). Hidden on paired devices.

### Choosing the agent

The New session dialog (`SpawnDialog`) starts its form with an **Agent** select
(`ui/src/components/AgentPicker.tsx`, reusable by any "new session" entry
point): Claude Code, Codex, OpenCode, Gemini CLI — only those whose binary the
daemon found (`*_available` on `/v1/status`), and hidden entirely when there is
one. The last choice is remembered per browser (`localStorage`
`caprock.spawn.agent`); a remembered agent that is no longer installed falls
back to the first one found. The model field follows the agent: Claude's and
Gemini's fixed lists — Claude's is the newest model of each family, each label
naming its exact version (*Opus 5.5*, never a bare *Opus*), opening on the
newest Opus, and a test fails the build when `pricing.json` carries a newer
model of a family than the list offers — Codex's own catalog from `GET /v1/agents/models` with its
configured default named, OpenCode a free-text `provider/model`. The
permission choices keep Claude's words and each says what it becomes for the
chosen agent, or that the agent's own config decides.

**Settings → New sessions → Start in** (`SpawnModeSetting`) is the mode both
new-session dialogs (`SpawnDialog`, `NewAgentSheet`) open on, stored by the
daemon (`spawn_permission_mode`), so the app, a browser and the phone agree.
Unset, the dialogs open on **Bypass · never asks** (the owner's decision, 2026-10-07; it was *Accept edits*); a bypass start from a paired phone is still confirmed inline. The daemon also applies
it to a start that names no mode — the project terminal's **New session
here**, a quick chat — and to a continue whose session recorded none. A mode
picked in a dialog is used for that session only; the preference changes only
in Settings.

A spawned Codex or OpenCode session whose first message has not linked yet
says the agent writes nothing until the first message, which Caprock links to
the session then; once linked, the header shows the agent's own id next to the agent's name.

## The terminal

A real terminal for sessions Caprock started, and the reason the first person
to use Caprock full-time stopped opening the Claude Code IDE. Never for a
session started elsewhere (rule 7).

**The terminal is dark in both themes.** Its palette is graphite —
`TERMINAL_THEME` in `ui/src/components/Terminal.tsx`, the dark tokens written
out — and its container is `bg-term-bg` with a `border-term-border` hairline,
two tokens no theme redefines; the page around it stays paper. TUIs draw for a
dark ground: on paper, Claude Code's dim text and status line were grey on
cream and unreadable (owner report, 2026-10-04). The palette used to be read
from the theme tokens once, when the terminal opened, so switching theme with a
terminal open left it in the other theme's colours — paper on a dark page.
Nothing re-themes it now, and a test toggles the theme both ways with a
terminal mounted.

**The keyboard first (2026-10-04).** Opening a session's terminal froze the
tab and typing lagged (owner report). A profile on a copy of his database with
a busy session found three things in the way, all now out of it:

- **WebGL ran before the socket.** Creating the WebGL context took 1.5 s in his
  Chrome and linking its shaders another 0.4 s in a headless profile, all
  synchronous, all before the socket was created. Now the terminal opens, takes
  focus and connects at once; the WebGL renderer is swapped in after the first
  output, once nobody has typed for 1.5 s (`WEBGL_QUIET_MS`). The DOM renderer
  draws until then.
- **The socket waited for the session's figures.** The terminal mounted only
  after `GET /v1/sessions/{id}` answered — 3.3 s on a busy daemon in one run.
  On the Terminal tab it now mounts before the detail arrives, assuming the
  session is Caprock's; the daemon holds sockets only for processes it started
  (rule 7), and the panel corrects itself when the detail lands. One element
  serves both layouts, so the detail arriving re-renders it rather than
  dropping the socket.
- **The figures were refetched on every live event.** On the Terminal tab the
  detail (about 500 KB for a long session) is polled every 30 s instead.

Measured in headless Chrome against that copy, with a fake `claude` printing
4000 coloured lines and a 12 fps spinner: before, keys typed on open went
nowhere until the terminal was clicked, the first echo came at 1.2–1.6 s, and
a key's dispatch blocked for up to 200–290 ms; after, keys typed on open reach
the session, the first echo comes at 0.4–0.8 s (one cold-cache run at 2.9 s),
and a key's dispatch blocks for 13–94 ms.

**It says when it is starting.** A resumed session can take half a minute to
print anything, and a black panel cannot be told from a broken one. Until the
first bytes arrive the panel says "Starting the session… N s"; after 30 s with
nothing (`START_TIMEOUT_MS`), or when the socket closes first, it says so and
offers **Retry**, which reconnects. The first output also triggers one fit and
one size message, so the TUI draws for the real size.

### From a phone

A phone the owner let control sessions ([ADR-034](08-decisions.md)) gets the
controls a viewer does not: **+ New session** on Now, the Terminal tab,
pause/resume/kill, continue, and approve/reject on Tasks. `useCanControl`
(`ui/src/lib/useCanControl.ts`) asks `GET /v1/pair/me` on load, every 15 s, on
focus and on every screen change, so a phone that loses control stops drawing
them; the daemon refuses them either way.

- **New session** on a phone is the machine's dialog: the path field (16px, no
  autofocus, so the keyboard does not cover the picker), **Recent** and
  **Browse** (rooted inside home), and Advanced (create the folder, worktree).
  The daemon refuses a folder outside home. Every permission mode is offered;
  **Bypass** asks once, inline, before starting: "The agent won't ask before
  running commands or editing files. Start?" with **Back** and **Start in
  bypass** (ADR-034). Not a browser `confirm()`: on a phone that is dismissed
  unread, and some in-app browsers suppress it.
- **The keys bar** (`TerminalKeys`) sits under the terminal: a 16px field (iOS
  zooms into anything smaller), full width on a row of its own — one line
  idle, growing to five, then scrolling — with **Photo** and **Send** under
  it, and Esc, Tab, ↑, ↓, ⏎ and Ctrl+C as 44px buttons (two rows of three
  below `sm`, where "Ctrl+C" filled its button in a row of six), because a
  phone keyboard has none of them and Claude Code's menus are answered with
  them. Send types the text, a line break inside it as
  ESC CR, then Enter 80 ms later — in one write a TUI reads the pair as a paste
  and keeps the Enter as a new line. It is always there on a phone and on any
  window narrower than `sm`; the terminal is 52vh there so the bar stays in
  view. The phone does not focus the canvas, which would raise the on-screen
  keyboard over the output. **Offline** (the terminal not live), Send holds
  the message in a list above the field — *Will send when connected*, with
  **Edit** — and sends it on reconnect if no permission prompt waits;
  otherwise it stays as *Not sent — a permission prompt is waiting* (or *the
  session ended*) with **Send now**. The six keys, and Send on an empty
  field, are refused while not live, with a notice that keys are never
  queued ([21-app.md § Phase A](21-app.md#phase-a--resilience-and-starting-work-p0)).
- **Photo** in the keys bar opens `<input type=file accept="image/*" multiple>`
  — no `capture`, which would make iOS open the camera only; without it the
  picker offers the camera and the library both. A photo larger than 2048 px
  on its long side or 1.5 MB is drawn at 2048 px and re-encoded as JPEG 0.85
  (`lib/downscale.ts`; a 12 MP photo is 3–6 MB and the paste limit is 10 MB),
  then goes the way a dropped file does: `POST /v1/paste`, and its quoted path
  typed into the session.
- **Permission prompt buttons** (`PermissionPrompt`, ADR-035). When an owned
  Claude Code session waits on a permission prompt, a card names the tool and
  shows its command or file, with **Yes**, the second option when Claude Code
  offers one (its label: *Yes, and don't ask again*, *Yes, allow all edits
  this session*, *Yes, and allow this folder*), and **No**, each 48px. Under
  the terminal on the Terminal tab, and above the tabs on every other one,
  because a phone opens on Timeline. A viewer sees the question without
  buttons. It goes away when anything answers the prompt, the terminal
  included. Each button names its key — **Y**, **A**, **N** — and beside them
  *Keys work from the terminal · ↵ Yes · Esc No*: the card and the terminal's
  own menu are one question, not two. Y, A and N answer from the asking
  session's terminal (marked `data-term-session`) and are kept from it;
  Enter and Esc there go to Claude Code's menu. It never takes focus. Above
  the tabs on the session screen — no terminal of the session on the page,
  which is where a phone answers — the keys and the line are left out
  (`keys={false}`).
  - *A prompt settled out of sight.* A request that timed out, or one a
    check denied without a menu, sends no hook that clears it, and the card
    stayed until the turn ended. A button answered on a screen with no menu
    now drops the prompt (409, the card goes), and **×** hides it, typing
    nothing (`choice: "dismiss"`).
  - *Queued prompts.* Claude Code shows one dialog at a time and queues the
    rest; the card shows the oldest — the one on screen — and *· N more
    waiting* when others are queued behind it.
  - *Refused answers.* The daemon reads the menu on the session's screen
    before it types and picks the option by its text; when the option is not
    there (auto mode's dialog has only *Yes* and *No*), it types nothing
    and answers 422. The card stays, with *that option is not
    on the prompt — answer in the terminal* under the buttons.
  - *Keys.* `Y` or Enter is Yes, `A` the second option (only when offered),
    `N` or Esc is No, drawn on the buttons (*Yes ↵*, *… A*, *No Esc*; the
    hint is not part of the button's name). Never while focus is in the
    terminal, a field or an editor — on the Terminal tab, where the card sits
    under the terminal, the terminal keeps its keys. Enter and Esc only with
    focus on the page or in the card; none while another dialog is open, from
    a hidden card, or from any but the newest card on the page.
- **Ask the agent from the diff.** On the Changes tab of a live session
  Caprock started, a controller phone can tap a line: a bar at the bottom
  offers **Ask the agent**, which opens the Terminal tab with the keys bar's
  field holding "In <file> around line N: " and focused (`lib/draft.ts`).
  Nothing is sent until Send. A viewer's lines are not tappable, and the
  machine itself types into the terminal directly, so it is not offered there.
- **Commit from the session** (`SessionCommit.tsx`). The Changes tab opens
  with an *Uncommitted* panel for the session's worktree: the project whose
  root holds the session (longest wins) and git's name for its worktree
  (`worktreeKeyOf`), never a guess — a worktree the project does not list
  says to commit on the machine, and a repository not listed offers *Add as
  a project*. Rows are 44 px: tap to stage or unstage (a tick shows staged;
  nothing ticked commits everything), then the shared `CommitBox` (message,
  *Use the agent's summary*, Commit, Commit & Push) and `RemoteActions`
  (Fetch, Pull, Push). A viewer sees the list and a line saying where
  committing happens. The branch-against-trunk diff below is unchanged.
  Below it, the worktree's pull request (`PullRequestCard`, WP-19): the
  same state as the desktop strip, readable by a viewer; a controller also
  gets *Open a pull request* (the same form, 44 px fields). The clone mode
  of *Start work* shows the repository picker once GitHub is connected on
  the computer.
- **Start work** (WP-15, `#/start`, `components/NewProject.tsx`). A
  controller phone gets a thumb-sized *+ Start work · clone, new project,
  worktree* row on Now. The page has three modes — **Clone** (an `https://`
  or `git@host:path` address and *Clone into*, a folder under home),
  **New project** and **Worktree** — then **Start an agent here**, which opens
  the spawn dialog and lands on the session's Chat. A clone in progress is
  kept in localStorage with its `op_id` and followed again after a drop or a
  reload (`lib/startwork.ts`), never sent twice. A viewer is not offered it,
  and the daemon refuses it.
- **Control taken away mid-session** closes the socket with 1008 and the
  terminal says so instead of reconnecting.
- **On the home screen** (`ui/public/manifest.json`, the `apple-*` tags in
  `ui/index.html`): standalone, the favicon's mark as the icon
  (`ui/icons/*.svg` → `scripts/make-icons.sh`), `theme-color` = the header's
  `--color-panel` for dark, paper and white, kept in step by `lib/theme.ts`.
  `viewport-fit=cover` with the status bar `black-translucent`: the sticky
  header pads itself by `safe-area-inset-top`, so its colour runs under the
  clock, and `body` pads the left, right and bottom insets. iOS gives a
  home-screen app its own storage, so it starts unpaired; the pair screen
  detects standalone (`display-mode: standalone` / `navigator.standalone`),
  asks for the typed code — a scanned QR opens Safari, not the app — and names
  the device "iPhone · home screen". WebKit counts a home-screen app's days of
  use apart from Safari's for its seven-day storage cap, so the token lasts
  while the app is used.
  **No service worker:** figures must never be served stale, and a LAN or
  Tailscale `http://` origin is not a secure context, where none can register.

### The scrolling rule

`lib/useStickToBottom.ts` with the `NewPill` component (WP-11): a list follows
new rows only within 4 px of its live edge; elsewhere the first visible row and
its offset are recorded and restored after every change (a MutationObserver,
before paint; `overflow-anchor` off so Safari and Chrome behave alike); a
"↓ N new" pill counts what arrived and jumps back. It serves lists that grow
downwards and newest-first feeds (`edge: 'top'`): the session timeline and the
activity feed use it now. xterm.js already keeps a scrolled-up viewport still;
the app's terminal adds the "↓ N new lines" pill. Tests: 200 rows streamed
while scrolled up leave the first visible row within ±1 px, both directions,
and a trimmed capped list keeps its row (`useStickToBottom.test.tsx`); in
headless Chrome at 1440×900, the app terminal scrolled up while ~1,100 lines
streamed was pixel-identical before and after, with the pill reading
"↓ 990 new lines" (2026-10-05). The chat view uses it too (bottom edge); its
"load earlier" line has no height of its own, because older messages are
inserted below it and the first visible row with a height is the anchor. That
line also carries the auto top margin that holds a short conversation at the
bottom of the log. The dashboard terminal fits again when xterm's grid changes
size inside an unchanged box: the WebGL renderer, swapped in late, measures a
taller cell and kept the row count, and at 390 px the grid ran 62 px past its
box and over the keys bar's field.

## Kept figures (stale-while-revalidate)

The slow figures show the last answer this browser saw while the fresh one is
read (`ui/src/lib/swr.ts`, the `cache` option of `useApi`). Owner report,
2026-10-04: Now sat on dashes while the daemon was busy.

- **What is kept** — Now's Today, plan limits, all-time and Projects; the
  Lifetime screen; History; and per session, the header figures (events and
  files dropped), for the 30 most recently viewed sessions. Never event
  streams or terminal data: those are about now.
- **How it is marked** — "updated N min ago · refreshing" beside the panel,
  and nothing about now (health, burn, controls, the active count, the
  timeline) is drawn from a kept copy.
- **Limits** — one entry per endpoint and query, the latest answer only; an
  answer over 200,000 characters is not kept; the total stays under 1,000,000
  by dropping the oldest. The key prefix carries a version, and entries under
  another version are deleted on load. Every storage access is in try/catch,
  so a private window or a full quota only means no copy.

**The socket carries two things, told apart by frame type.** Binary is what the
user typed, written to the PTY byte for byte. Text is a control message —
today only `{"resize":{"cols":N,"rows":N}}`. See
[03-contracts.md](03-contracts.md).

**Size is sent, not assumed.** `fit()` resizes the canvas and nothing else, and
for a long time nothing told the daemon: `Resize` was declared on the agents
interface and called from nowhere, so a PTY kept the size it was born with —
120×40 by default — for its whole life. Claude Code lays its menus out to the
terminal size, so on any other window it drew an interface for a screen the
user did not have, and arrow keys moved a selection nobody could see. Reported
as *"only Enter works"*, which is what that looks like from outside.

**Every newline key sends `ESC CR` (`1b 0d`)** — Shift+Enter, Option+Enter,
Ctrl+Enter and Ctrl+J all send it. It is what a terminal sends for Alt+Enter,
and what Claude Code's own macOS instructions tell people to bind Option+Enter
to.

Getting there took four wrong answers, and the reason they survived is worth
more than the value itself: **three of them were tested on an empty prompt,
where a newline key that submits and a newline key that adds a line look
identical.** With text already typed, the difference is the whole feature.

The four attempts, in the order they were made:

- **CSI u** (`ESC [ 13 ; 2 u`) is what a terminal sends *after* negotiating the
  kitty keyboard protocol. This one writes into a PTY directly and never
  negotiates, so the sequence did nothing at all.
- **A bare line feed** (`0x0A`, what Ctrl+J sends) is read by Claude Code as
  *submit*. The user who reported it described the tell exactly: on an empty
  prompt it looked like a newline, because there was nothing to submit, and the
  moment he typed anything the same key sent his message.

The lesson is cheaper than the two rounds it cost: when a product configures a
terminal for itself, read that configuration instead of inferring the protocol
from its documentation.

Backslash-then-Enter needs nothing from us: the backslash is already in the
line and Claude Code reads the pair itself.

**Copy and paste follow VS Code's rule**, because it is the one people already
have in their fingers. **Ctrl+C copies when something is selected and
interrupts when nothing is** — a person who has just dragged across output
means copy; a person who has not means stop. On macOS the question never
arises, since Cmd+C and Ctrl+C are different keys, so Ctrl+C stays SIGINT
there whatever is selected. Ctrl+Shift+C/V elsewhere, deliberately distinct
from Ctrl+C so interrupting keeps its key.

**A paste is the browser's own event, handled by xterm, and never a clipboard
read of ours.** Cmd+V and Ctrl+Shift+V return `false` from the key handler so
xterm does not send `^V`, and the browser's paste reaches xterm's textarea,
which applies bracketed paste when the process asked for it — a multi-line
paste has to arrive as one paste, not as N submitted lines. Until 2026-09-29 a
paste key *also* read the clipboard and called `term.paste()`; returning
`false` does not cancel the browser's paste, so every paste went out twice
whenever the clipboard read was allowed (FB-034). The native path needs no
clipboard permission either, which Safari asks for on every read.

**A terminal attached late still knows the modes the session set.** The daemon
replays the last 256 KB of output to a terminal that connects, and Claude Code
turns bracketed paste on once, at startup — measured: 182 KB of redraws with no
second `ESC[?2004h`. Past that point a reattached terminal (a tab switch, a
reload) had bracketed paste off, so a long paste went in raw and was not
collapsed. The output buffer remembers the last value of DEC private modes 1
(cursor keys), 25 (cursor), 1004 (focus) and 2004 (bracketed paste) and sends
them ahead of the snapshot (`internal/agents/modes.go`).

**WebGL where the machine has it.** The canvas renderer repaints the whole
grid; the WebGL one draws from a texture atlas, which is the difference
between a build log scrolling and the tab stuttering. Every failure path falls
back to canvas: no WebGL, a driver that refuses, or a context lost on
sleep/wake. A slower terminal is a cost; a blank one is a broken product —
and that fallback is tested by making the mock throw the way the real xterm
does, after a first attempt whose mock silently never fired because the real
addon class minifies to a one-letter name.

Scrollback is 10,000 lines: a build log passes 5,000 easily, and losing the
start of what you are reading is where a terminal stops being one you can work
in.

**Paste or drop files and Claude Code can read them.** A browser hands over a
file's bytes and never a path — there is no path for something copied out of a
screenshot tool, and a file dragged from Finder arrives as a name and contents
— while Claude Code reads files by path. So each file goes to `POST /v1/paste`
with its name, the daemon writes it to `<data_dir>/paste/<stamp>-<random>/`
under that name, sanitised, and the path it returns is typed into the session,
quoted (a macOS data directory contains "Application Support", and unquoted
that is two arguments) and followed by a space. Claude reads `contract.pdf`,
not a timestamp.

Every dropped or pasted file is sent, one at a time and in order, so several
paths land in the order they were dropped. The daemon accepts images, PDF,
text, Office documents, data and source files by **extension**, because a
browser leaves the type empty for Markdown, CSV, JSON and source files (the
list and the naming rules: [03-contracts.md](03-contracts.md)). A refused or
failed file prints a yellow `[caprock: <name>: …]` line naming what is
accepted, and the rest still go. Until 2026-10-04 only the first file was sent
and only by MIME type, so a Markdown file dragged from Finder came back
"415 Unsupported Media Type".

An ordinary text paste is left alone: xterm already handles it and already
applies bracketed paste, so intercepting it would turn a multi-line paste into
several submitted lines.

**What is checked, and how.** `testdata/ptyecho` prints the bytes it receives,
so `-tags ptyspike` can assert that an arrow key arrives as `1b 5b 41` and a
resize reaches the process — verified against `stty size`, which is the
kernel's view rather than our own struct. Asserting on our own bookkeeping
would have passed while `Resize` did nothing at all, which is exactly what it
did.

## Tasks (kanban)

- Columns: inbox → assigned → in-progress → verifying → done / needs-you.
- Tasks are files on disk (`tasks/<id>.md` with YAML frontmatter); the board renders them. Format: [05-orchestration.md § Task file](05-orchestration.md#task-file).
- "needs-you" = approvals queue (spend thresholds, destructive ops, scope changes).
- Shipped in v0.3.0.
- **A card opens to the work.** Any task with an assignee is clickable and opens a drawer answering, in this order: what changed (the file list and patches from `GET /v1/sessions/{id}/diff`, reached through the newest session in the detail's `work.sessions`), what proved it (the latest verification round — command and exit code), where the work is (branch, worktree, repo), and how to take it (`git merge --no-ff caprock/<worker>`, copyable). The card itself carries the branch name so the board answers "where did that go?" without opening anything. Before this, a card was a title, an id and a dollar figure, and the diff endpoint had no reference anywhere in the UI — which is the whole reason the feature read as having no output.
- **The merge command is text, not a button.** It writes to the user's repository; a dashboard that runs git on your branch without you having read the command first is not something a local-first tool should ship. `Copyable` (lifted out of `UpdateBanner` into `components/ui.tsx`) is the shared primitive.
- **The off state is three steps and a button, not three paragraphs and a command.** It carries the concept, not the flag: the same three facts that decide whether anyone runs this — the work happens in a separate git worktree, **Caprock** runs the checks rather than the agent, and the queue directory is created for them — plus the limit that it suits independent tasks only. They arrive as a numbered strip (*you write a task* → *Caprock runs it* → *Caprock checks it*), because nobody reads a wall of text to decide whether to try a button. "Phase 2" and "hive" are our vocabulary and appear in no user-facing string, here or in the CLI.
- **Turning it on is a click, not a command to paste elsewhere.** The screen previously handed over `caprock up --hive ~/caprock-tasks`, which is the opposite of a start button: the one control the feature needed lived in a terminal. `POST /v1/hive` ([03-contracts.md](03-contracts.md)) turns the runner on over the running daemon, and the board replaces the off state in place — no restart. The paths it will use are the daemon's own suggestions (`suggested_hive`, `suggested_repo`), shown filled in and editable.
- **It confirms before it arms.** Enabling this is what lets Caprock spawn Claude sessions with permission prompts skipped, so a dialog names the queue directory and the repository, says in three lines what will happen — the directory is created, sessions may run with prompts skipped one worktree each, and *nothing starts yet* — and only then offers the button. A silent one-click that begins spawning agents is not something a local-first tool should ship; neither is a dialog nobody can read, so it is three short lines and two named paths.
- **The empty board says which button comes first.** Six empty columns and two buttons do not: an orchestrator started over an empty board has nothing to assign. One line — *start here: + New task, then ▶ Start orchestrator* — appears only while there is no task at all, and disappears the moment there is something to look at.

The header carries the **running version** at all times — it was previously only on the status page, and "which build am I on?" is asked far more often than that placement implied. With release checks on and a newer version available it reads `v0.9.0 → v0.9.4` in the accent colour and links to the notice. The chip is a button. It used to be a label that said a newer release existed and stopped there — which answers the half of the question nobody needs help with. **Caprock does not update itself, and the dialog says so.** A daemon that overwrites its own running binary — as root on some install paths — is a worse thing to own than a stale version. Stating it once beats leaving a person hunting for a button that should not exist.

## Update notice

When a newer release exists, Now leads with a line naming it and **the exact command for how this copy was installed** (`brew update && brew upgrade caprock`, `scoop update caprock`, `go install …@latest`), one click to copy. When no package manager owns the binary it links to the release page instead. The Homebrew command refreshes the tap first, and that is load-bearing: a tap is not served by the Homebrew API but read from a local git clone, which `brew upgrade` refreshes only through auto-update — at most once every 24 hours. A user who ran any brew command earlier the same day is told `already installed` for a release that has been public for hours, and the command Caprock gave them looks broken. Reported by a user on the day v0.31.1 shipped.

There is deliberately **no "update now" button**: upgrading replaces the running binary, so the daemon would be killing the process running the command, and executing a package manager on the user's behalf from a web page is a surface a local-first tool should not open. You run one line in your own terminal, where you can see what it does.

When the upgrade would end sessions Caprock started, the line says how many
will close. Since [ADR-033](08-decisions.md#adr-033--an-owned-session-outlives-the-daemon-its-terminal-lives-in-a-pty-host)
a session whose terminal is in a pty-host is picked back up after the restart
and is not counted (`survives_restart`); what is counted is a session in the
daemon's own PTY, the fallback when a holder could not start.

**An open terminal reconnects across the restart, and loses nothing.** The
daemon closes the socket with code 1000 when the session's process exits, and
only that prints `[session ended]`. Any other close is the connection —
Caprock restarting, a dropped network, a phone waking — and the terminal
reconnects forever (full jitter from 0.5 s to a 15 s cap; at once when the
page becomes visible, comes online, is restored from the back/forward cache
or changes network — [03-contracts.md § Client reconnect policy](03-contracts.md#client-reconnect-policy)) over [terminal protocol v2](03-contracts.md#terminal-socket-protocol-v2):
it asks for the output after the last byte it has, so the screen and the
scrollback stay as they were and nobody reading back is moved, and it resends
what was typed and not yet acknowledged, which the session types once. A pill
over the terminal shows the connection state (**Reconnecting (n) · next try
in s**, **Catching up…**, **Control revoked — reason**) and, while
reconnecting, **Typed keys will be sent**;
it used to write "reconnecting" into the terminal itself, retry every second
for a minute, then ask for a reload. Up to 4 KB typed while offline is kept;
past that the pill says the extra keys were not. A daemon from before v2 is
still spoken to in version 1, which clears and repaints on reconnect.

**In the desktop app** (F12) the notice is quiet: *vX.Y.Z is out* in the
status strip, which opens a small panel with the command for each part this
machine installed through Homebrew — the app's cask (`brew update && brew
upgrade --cask caprock-app`, `app_command`) first, then the daemon's
formula (`command`) — or a pointer to the release page when neither is
known, *what's new*, and **Not now**, which hides that version (the same
`caprock.update.dismissed` key as the banner, so dismissing in one place
dismisses in both). It reads `GET /v1/update` every 10 minutes, which never
touches the network; with checks off it shows nothing. The daemon checks at
most every 6 hours, conditionally (ETag).

**Since F20** (ADR-042) an app that can replace itself also announces a
newer version once in a bottom-right card (`AppUpdateToast`: **Update and
restart**, *What's new*, **Later**, which hides the card for that version
only, under its own key `caprock.update.toastSeen`; the card shows progress
while it downloads). The strip's line turns into one click: **Update to vX.Y.Z — Restart** (newer than the *app's* version),
then *Downloading vX.Y.Z* with a bar and a percentage, *Installing … —
restarting…*, and the restart; or **Update failed**, which opens to the
reason, **Try again**, the release page and **Not now**. A ▾ beside the
button opens *what's new* and **Not now**. A check by hand (the app menu, the
tray menu, the palette) shows *Checking for updates…* and then the offer or
*Caprock is up to date* for 6 seconds, whatever the release-check setting. A
`.deb`/`.rpm` install or a development build keeps the command line above,
with the reason it cannot update itself. On its first launch the app asks
once in a small card above the strip — *Check for updates automatically?*,
**Yes** focused — instead of the dashboard banner's offer, which the app does
not show ([21-app.md § Updates](21-app.md#updates)).

Because the check is the only outbound call Caprock makes, the same strip is where it is switched on — offered once, in plain words, with "no thanks" remembered. `not now` dismisses a specific version, so the next release speaks up again.

### Open Caprock on your phone

Three numbered steps and one button. The steps: your phone and this Mac (PC,
computer — named from the browser) are on the same Wi-Fi; press **Show a code**
and point the phone's camera at it; the phone appears below, removable any
time. When the address is a Tailscale one, step 1 says Tailscale must be on
both instead.

- **Show a code** does everything in one press: turns network access on
  (`POST /v1/pair/lan`) if it is off, issues a code, and shows a **QR code**
  beside the six digits in 40px type, the address to type for a phone whose
  camera will not cooperate, and a `m:ss` countdown. The QR code encodes
  `<address>/#/pair?code=NNNNNN`; the phone's pairing page reads the code from
  the link, pairs by itself, and wipes it from the address bar. When the
  daemon listens on more than one address (WP-15), a choice above the code
  picks which one it carries — *Wi-Fi*, *Tailscale*, *Tailscale name* — each
  with one line on where it works ("Works anywhere your phone has Tailscale
  on — even on mobile data."). Without Tailscale the panel says a phone off
  the Wi-Fi cannot reach Caprock and links to Tailscale's download page. **New code**
  replaces it; **Cancel** withdraws it on the daemon (`DELETE /v1/pair/code`).
- **The QR code is drawn in the browser** by `ui/src/lib/qr.ts` (byte mode,
  level M, versions 1–10, no dependency), black on white whatever the theme.
  The link carries a code that lets a device in; it is not sent anywhere to be
  rendered.
- **The state, at a glance**, in the section's corner: `Off`, `Off · 1 phone
  paired`, `Waiting for your phone…`, `1 phone connected`, `On · nothing paired
  yet` ("device" instead of "phone" unless every name looks like one). While a
  code is out the state is polled every 1.5 s, so a phone that pairs shows up
  within a couple of seconds, with a line saying it is connected and where
  Caprock lives on it.
- **Paired devices** are listed with their name and the first four characters
  of their id, their role ("view only" or "can control sessions"), when each
  was last seen and when it was paired — two phones of one model otherwise read
  as the same row. The pairing page offers a name of device and browser
  ("iPhone · Safari"); a browser on the machine itself that paired through the
  network address is named "This computer · …" by the daemon. Each row has a
  **Remove** button — while network access is off too, from `devices.json` —
  and one button for control: **Let it control sessions**, or **Take control
  away**
  ([ADR-034](08-decisions.md)). Taking it away holds from the phone's next
  request, and an open terminal on it stops taking keys.
- **The security model is one line**: only phones you pair get in, they can
  look but not change anything unless they are let control sessions, and it
  switches off when Caprock restarts.
  Below it: "Not on the same Wi-Fi? Install Tailscale on both — then it works
  from anywhere" (or, when the address is already Tailscale's, that it works
  anywhere the phone has Tailscale too). **Turn off** and the listening address
  sit at the bottom while it is on.

### Storage

A **Storage** section answers "how much does all this take, and what is it?"
— on Settings rather than a screen of its own, because it is a figure checked
once in a while and not a view anyone works in. It reads `GET /v1/storage` once
a minute ([03-contracts.md § Storage](03-contracts.md#storage)) and is shown to a
paired device too, since it changes nothing. The headline stays on screen; the
bars and the levers are under **Details**.

- **The headline** is the data directory's total, the growth rate, and how many
  events since when. The growth rate is labelled "estimate, last 30 days" and
  says how it was made on hover; it is the panel's only derived figure.
- **On disk** splits the directory into the events table, its indexes, the
  other tables, free pages (when there are any), the write-ahead log, logs
  (every `*.log` as one row) and whatever else is there, each with its size
  and share of the total.
- **Recorded, by agent / by kind** split the bytes the events recorded — the
  raw payload, not the file — because indexes and page overhead belong to
  nobody in particular. The shares are of that payload.
- **The levers** are stated as sentences under the bars. Retention: whether
  events are kept forever, how much is older than 90 and 30 days, how to set
  `retention_days`, and that the file does not shrink — deleted rows free space
  that new events reuse. Compaction: how much of the file is free pages. There
  is **no Compact button**; the manual `caprock down` + `sqlite3 … VACUUM`
  appears only when the free pages pass 64 MB, and otherwise the panel says a
  compaction would give back next to nothing. The reasons (a second copy's worth
  of disk, the write lock held for the whole run) are in the contract.

## Plan value

A **plan chip in the header** states how you pay for Claude Code — Pro, Max, a Team seat, a custom monthly price, or metered (API key / Bedrock / Vertex / Enterprise at API rates). Caprock cannot detect the plan and never guesses, so the chip reads `set plan` until you say; it is one click from being changed when your plan changes, and the value is stored locally in `config.json`.

The Cost screen then leads with what the measured usage is worth, scaled to the selected range:

- **Flat plan** — a single multiple ("35.7×") over two lines: what you pay for the window, and what the same usage would have cost at API list price. Never phrased as money saved: without the plan you would not have run that much, so "saved $X" would be an invented number.
- **Metered** — no multiple at all. The API-list figure is approximately the real bill, so it is labelled as spend and explicitly marked "not a saving".
- **Not stated** — nothing is claimed; the panel invites you to set the plan.

### Incomplete and background usage

When a public model id has no price, the Cost, Now, and History screens show a
compact **Partial cost** note with the measured token count and model id. The
primary row states only that the total is incomplete; `copy model` copies the
id without usage or project data, `report` opens a prefilled privacy-safe issue,
and `why?` reveals that the total is a lower bound and that no manual price is
expected. It never calls the usage free. The issue link contains model ids only,
not prompts, paths, project names, token counts, or costs.

Known internal machinery is a different state. `codex-auto-review` is shown as
muted **Background usage** with measured tokens and no warning or action;
it produces no warning, no user session, no turn/cost total, and no report
action. The raw events remain available for audit, while user totals stay
reconcilable.

Rules are unit-tested in `ui/src/components/Unpriced.test.tsx`.

## Offers, and when they are allowed to speak

Several surfaces in the dashboard point at something that costs money — the
team tier, the paid features, and the share card that carries the product's name
off the machine. Each opens with a fact from the reader's own screen, quotes no
price, and either appears only on a condition or can be put away for a month.

**Caprock for Teams is explained in place.** Every team surface — the Cost
banner, the Projects line and the footer — opens the same dialog
(`TeamsModal`) rather than the website. Owner request, 2026-10-03: the footer
link alone sent people off the dashboard to learn what the offer even was.

**Both upsell dialogs show before they tell** (owner, 2026-10-04: the text-wall
versions were "bad"). They share one frame, `UpsellDialog`: a picture of what
you get first, drawn in the Week card's language (its ground, characters and
big figures), then a few lines with icons, then the two ways forward. Every
figure in a picture is an example and the picture carries an **Example** tag,
in its visible text and its `aria-label` (rule 6); tests assert both.

- **Teams** pictures an example team's week — laptops, PRs, ≈cost per PR, the
  share re-reading context, an agent strip and a repository strip — then this
  machine's own spend when the caller has it, four benefits (who is eating the
  budget, loops on every machine, every agent in one total, what the money
  bought), one trust line exactly as the team page states it (the team's own
  infrastructure, counters only, prompts and code never leave a laptop) and one
  on the price's shape (one flat price, never per seat — no figure; the
  pricing page owns it). **Book a demo** is the amber primary, **See the team
  page** the outline secondary.
- **Premium** (`PremiumModal`, one component for every paid feature — the
  header chip, the hint, the banner and each locked panel open it) pictures the
  feature working: the daily cap stopping at its line, the plan window at 90%
  with Caprock's sessions paused until the reset, a question asked of
  Gemini about your own sessions with its cost beside the Claude spend, the
  Monday message from your own bot, a tool opened into its commands with
  output and failure rate per group (example figures, labelled so). Then three lines with icons and the setup
  the feature demands, named before payment.
- **Prices exactly as caprock.dev sells them:** $30 a year and $100 once, with
  **Best value** on the lifetime as the site marks it; the monthly price is not
  linked from the site and is not offered here. Figures come from
  `GET /v1/premium`. The buy buttons are the product's amber — filled for the
  recommended one, outline for the other — not the premium ultramarine, which
  made them read as an advert. The free-forever line stays at the foot, smaller.
- **Dialog behaviour:** Escape, the backdrop and both close controls close it;
  focus moves into it on open, Tab stays inside, and focus returns to the
  opener on close. All links open a new tab. At 390 px the pictures fit and the
  two price cards stack.

The rule behind all of them: **an offer that is always visible is wallpaper** —
read once, ignored after, and faintly grubby on a tool someone installed for
its own sake. An offer tied to a condition is either useful or absent.

| Surface           | Appears when                                    | Where                 |
| ----------------- | ----------------------------------------------- | --------------------- |
| Caprock for Teams | 10 or more repositories in the selected range   | Projects panel, Now   |
| Teams banner      | 7d/30d/all with spend; not dismissed this month | Cost                  |
| Premium banner    | measured spend; not dismissed this month        | Now, Lifetime         |
| The spend cap     | today has cost ≥ 1.5× the 30-day median day     | All-time line, Now    |
| Plan-window stop  | a plan window ≥ 90%, no licence                 | Now (plan-limit row)  |
| Share the card    | total is within 10% above a round figure        | All-time panel header |

**The thresholds are judgement, not measurement.** Nobody has data on which
number converts; they were picked to be defensible rather than optimal, and
each is one line to change:

- **Ten repositories.** Below it, "your team" is a guess about someone who may
  well work alone, and guessing at a stranger's situation inside their own
  dashboard is how a tool starts feeling like a funnel. Ten is roughly where a
  single-person explanation stops being the obvious one.
- **1.5× the median day.** Against the **median**, never the mean: one runaway
  afternoon drags a mean upward and would then suppress the hint on exactly the
  days that follow it. Fewer than seven days of spend is not a baseline, so
  nothing is shown until there is one.
- **Within a tenth of a round figure.** People post milestones, not arbitrary
  Tuesdays. Crossing $10,000 is worth a mention for a while; by $18,000 the
  moment has gone and a button still announcing it is noise.

The share card carries no project names and no session identifiers — a share
button that quietly publishes which repositories someone works on is a trap —
and it carries the same caveat every cost figure does, because a dollar amount
posted without it reads as a bill somebody paid.

Rules are unit-tested in `Projects.test.tsx`, `Lifetime.test.tsx` and
`ShareCard.test.tsx`, including the absences: the team line is pinned to stay
away at six repositories, and the cap hint to stay away on an ordinary day.

## Hierarchy

The dashboard is dense on purpose, but density without hierarchy is texture. A review found 86% of its type sitting between 10px and 12px, no `font-semibold` anywhere, and the root at `14px` — which silently rendered every rem-based class 12.5% smaller than the identical class on the marketing site.

- **`Stat` has three sizes.** `hero` (34px) for the one figure a screen is about, `default` (24px), `compact` (17px) for reference figures in dense rows. Values are `font-semibold`: weight separates a number from its neighbours without spending a pixel of density, which is exactly what a dense surface needs. Uniform sizing made a row of six an inventory list with no landing point.
- **Cost leads, and carries the accent.** It previously sat fourth of six at the same weight as a turn counter, while the two *tinted* cells were cache hit and burn — so colour pointed away from the money. Now the day's cost is the hero, the per-repo costs are accent, and everything else steps down.
- **Panels are objects, not outlines.** `--shadow-panel` plus a recessed header band: the panel-to-page luminance step is 6 of 255, so without a shadow the edge is guesswork.
- **A tone means "act", not "a value exists".** Cache hit was green whenever the rate exceeded 50% — it is ~99% permanently on Claude Code, so the signal was always on, which teaches the eye that green means nothing. It now speaks only below 90%, where it means a prefix broke. Burn lost its permanent tint for the same reason.

What was deliberately *not* done: making everything bigger. Six stats at 34px would still be six equal cells — a bigger flat field, not a hierarchy. The gain comes from ratio and weight, and from stepping reference figures *down* to make room.

## Loading states

Panels show **placeholder rows** while their first fetch is in flight, never an empty state. Screens used to test `list.length === 0` without asking whether the data had arrived, so the first paint of Cost, History, Now, Projects and Answers announced "No history yet" and then replaced it with real numbers — telling a new user the product has nothing for them at the exact moment it is fetching everything. `Skeleton` in `ui/src/components/ui.tsx`; it is `aria-hidden`, since it carries no information, and its pulse respects `prefers-reduced-motion`.

An empty state is now only shown when the answer really is empty, which is what makes it worth reading.

## Charts

The daily-cost bars on **Cost** and **History** answer on hover and on focus: the bar highlights, its date label brightens, and the panel header swaps the range total for that day's cost, tokens and session count. Reported by an early user as "I expected something to happen and nothing did" — the bars previously carried only a native `title` tooltip, which is a real answer that arrives after a browser delay, in the OS font, detached from the chart. Long enough to read as broken.

Bars are `<button>`s so keyboard users get the same readout via focus, and a zero-cost day still draws a visible sliver rather than vanishing. Implementation: `ui/src/components/BarChart.tsx`, unit-tested.

## Memory (what Claude actually said)

For a large share of sessions the deliverable is not the diff but the conclusion — "this is done, but I could not verify X; check with the team and then we finish it". Caprock always stored that paragraph and never showed it: the timeline rendered a 200-character slice of it on one line, so people copied it into a notepad or lost it to scrollback.

- **Memory** (top nav) searches Claude's prose across every session. Browsing shows substantive answers only, because most rows are one-line asides that would bury the conclusions; a search shows everything, since the user asked for those words. Each result names its repo and links to the session.
- **A session's Answers tab** lists that session's prose, newest first, with the short remarks collapsed behind a toggle. It read from every assistant turn on the machine until 2026-10-04 — the planner preferred the kind index to the session's own — which on the owner's database cost 3.3 s cold for a session of 21 turns; it is 20 ms on the session index. The same day it was found to show one line of a long Russian conversation: the prose had never been stored (see [03-contracts.md](03-contracts.md), parser v4). Prose wraps anywhere (`Prose`, `overflow-wrap: anywhere`): one long URL in a reply used to set the page's width.
- **The timeline expands into prose.** Expanding a `turn.assistant` or `turn.user` row now shows the full text with its formatting intact, and keeps the raw event behind a `raw event` disclosure rather than as the only thing on offer.

Long answers collapse at 600 characters with an exact character count on the expander (counted in characters, not bytes — the bug that started this counted bytes). Newlines are preserved: the structure of a summary is most of its readability. Subagent sidechains never appear — see [03-contracts.md](03-contracts.md) for why that filter lives in SQL rather than in the caller.

## Week

`#/week` (`?start=YYYY-MM-DD` to open a given week). A card of what this
machine's agents did in seven days, made to be posted, in two layouts at their
export sizes: **landscape 1200×675** (X, LinkedIn) and **portrait 1080×1350**
(Instagram, Telegram). Free, like everything that describes one machine; a
card across a team's machines belongs to the team tier and is not built here.

- **The card is the screen.** It is drawn at full size from theme tokens —
  graphite on dark, paper on light — and scaled to fit, and **Download PNG** /
  **Copy image** draw that same node with `html-to-image` (MIT, pinned,
  bundled). The fonts embedded are the bundled faces, read from the same
  origin; nothing is fetched off the machine.
- **The headline is the strongest measured thing, never a zero:** merged pull
  requests, else opened, else commits, else ≈lines, else sessions. The tally
  under it carries the other non-zero counts; the side column leads with
  money (list price, ≈cost per merged PR, share spent re-reading context).
- **Who did what** is drawn with the agent characters
  (`ui/src/components/Characters.tsx`): Claude Code's main threads, its
  subagents, and each other agent with its own sub-agents folded in. One line
  each — CI wait for Claude Code when it was measured, else PRs or sessions.
- **Callouts:** the longest loop (by the detector's rule; "≈" on its context
  cost) and the biggest session's share of the week. Portrait adds the PRs
  opened per day, or cost per day when no PR was opened.
- **Privacy:** no repository, path, prompt or session title is on the card;
  the endpoint does not send them. The footer says where the figures come from
  and what "≈" and "merged" mean.

Weeks are seven local days; the arrows step a week, the date label opens a
date picker, and the default ends today. Contract:
[03-contracts.md § The Week](03-contracts.md#the-week-get-v1week).

## Sharing figures

The card is drawn to look like the dashboard, not like an advert for it. What
people post is a screenshot of a thing working; a poster with one enormous
number reads as marketing and gets scrolled past, and the first draft of this
was exactly that poster.

It carries eight tiles — today, the week, the month, all time, the daily
average, tokens, cost per million, cache rate — over two breakdowns: where the
money went by model and what it went on by kind of work, each with a percentage
beside the figure. 1200×630, the size every social preview crops to.

**Three figures are deliberately absent.** The instantaneous burn rate, because
it read $7.33 one minute and $33.54 the next and a card lives in a feed for
weeks. Turns and tool calls, because they are counts of things nobody has a
feel for — tokens sit next to the money and explain it. And a session count,
which was the same problem in another unit; it became cost per million tokens,
the one figure that answers *dear or cheap* rather than *how much*.

**What must never appear on it**: a path separator. Model ids are the only
names on the card and they are public product names, but a gateway reports
`minimax/minimax-m3`, and a slash on an image somebody is about to post is
indistinguishable from a repository path. The vendor prefix is stripped and a
test asserts no `/` survives.

The caveat — *not a bill, and not money saved* — travels with the figure. A
dollar amount posted without it reads as a bill someone paid. It was lost once
during a rewrite and the test is what caught it.

**Two controls, because there are two jobs.** `ShareCard` is always in the ALL
TIME panel: whether someone's numbers are worth posting is their call, and a
person who wants to share should not wait for permission. `ShareNudge` is the
push, and waits for an occasion it can name in the reader's own numbers — a
round number crossed, the first full week, or a week a fifth clear of every
week before it. That last threshold matters: while usage grows, *highest ever*
is true nearly every week, and a prompt that fires weekly is one people stop
reading. Rate-limited to once a week and dismissible; rules in
`ui/src/lib/shareprompt.ts`. A third entry point sits in the header, because
the panel button is only reachable from Now.

**The dialog offers two things and names where each one goes.** It was three
paragraphs of caveats above a button labelled "Share…", and the owner could not
tell what pressing it would do; an ellipsis is not a destination. The privacy
line sits below the buttons — it answers "is this safe to post", which only
arises once "what happens if I press it" is settled.

**The native share sends the file alone.** `navigator.share({files, text})`
looks like a courtesy, but two payloads leave the receiving app to decide what
they mean and several resolve it as two items — macOS's Copy produced the card
twice. The card already carries every figure and the caveat, so the caption was
never load-bearing.

**Drawing and locking are separate states.** One flag doing both jobs meant
that clearing it early — so the label would stop saying "drawing…" while the OS
share sheet sat open — re-enabled the button underneath that sheet, and a
second press drew a second card. `drawing` labels; `locked` outlasts it.

**Two styles: Figures and Story.** Figures is the card above. Story is the
Week screen's card — the headline ("My agents shipped 129 PRs this week."),
the money beside it, who did what with their characters, the longest loop and
the biggest session — at 1200×675 or 1080×1350, for whichever period is
chosen. It reads `GET /v1/week?period=` and speaks in the period's words:
"today", "this week", "this month" (the last 30 days, with the dates on the
card) and "— all time". A day has no bar strip; a month's bars are weeks and
all time's are calendar months, summed, never averaged. Tiles with nothing in
them are left off, and every estimate keeps its "≈". The style and the size
are remembered per browser.

**Opening it shows a card at once.** It used to start from nothing: four
summary requests, the slowest several seconds on a large database, and an empty
box saying "drawing…" until all of them answered. Now the last figures for each
period are kept (in memory, and in localStorage for the next tab;
`ui/src/lib/sharecache.ts`) and drawn the moment the dialog opens, marked "from
14:03 · updating…" while the current ones are fetched behind them. With nothing
kept, the dialog draws the card's outline and ticks off each range as it
answers ("Reading this week ✓"), with the seconds elapsed. Hovering the Share
button starts the default card's requests, and the preview and the save share
one round of them. **Saving or sending always waits for the current figures**:
a card that leaves the machine never carries an earlier reading.

### The cache hit rate says what it means

The figure was shown alone and coloured amber below 90%, so everything above
that read identically — 99% and 91% looked the same, and neither said
anything, on a measurement that runs from 6% to 99.6% across real sessions
with a median of 93.6%.

One word now sits beside it: **outstanding** at 99% and above, **excellent**
from 98, **very good** from 96, **good** from 90, **ok** from 85, **low** below
that. The top of the range was one step where the eye reads several — 98% and
99% are not the same session and both said "outstanding" — so the two middle
words split the range a reader cares about and `good` moved down to make room.
The bands are set against the observed spread rather than picked for roundness,
and everything from `good` up shares one colour: the word carries the
distinction, not the hue.

**A caveat for whoever touches these next.** The distribution has moved a long
way since the bands were first set. Measured when the middle words were added,
the median hit rate is **99.98%** and **59% of sessions** land in the top band —
where the original intent was about one session in nine. So `excellent` and
`very good` describe roughly 3% of sessions each while `outstanding` describes
the majority. The bands are honest about what they measure; whether 99%+ still
earns a word is a separate question, left open rather than decided here. The
alternatives considered were moving the top band to 99.9% (where the mass
actually sits) or showing no word at all above 99%, on the grounds that a
number that high speaks for itself.

Three rules hold it in place.

- **It describes a state, not a performance.** The cache is Claude Code's
  doing and Caprock only reads it, so nothing here congratulates anyone.
- **`low` is a fact, not a verdict.** A short session has little to reuse; a
  low rate is the honest result of the work, not a fault, which is why it is
  not called *bad* or coloured red.
- **Nothing moves.** The dashboard sits open all day, and a flash that
  celebrates a good number is charming once and an irritation by the
  afternoon. Motion means live data on this dashboard and nothing else.

The middle band is deliberately uncoloured: colour means something here, and
an ordinary reading is not something. Bands live in `ui/src/lib/cachelevel.ts`
and are rendered by `CacheStat` — one component for the three screens that
show the figure, because three copies of a product decision drift.

## Visual direction (v0 tokens)

Utility-first "mission control" aesthetic — the opposite pole from Munder Difflin's toy-office charm; the personality comes from density and precision, not decoration.

- **Theme:** dark by default (ops-room); a light theme ships too, toggled from the header or chosen under Settings → Appearance (persisted to localStorage; follows `prefers-color-scheme` when unset). Both are defined as semantic tokens in `ui/src/design/tokens.css` — the light palette redefines the same variables under `[data-theme="light"]`, so every screen and the terminal follow along. **The light theme has two tones** (2026-10-03): `paper`, the cream ground caprock.dev uses, and `white`, the original. Paper is the default (`DEFAULT_TONE` in `ui/src/lib/theme.ts`, mirrored in `index.html`); it overrides only the surface tokens under `[data-theme="light"][data-tone="paper"]`. Settings → Appearance → Light theme switches per browser (`caprock-light-tone` in localStorage; only an explicit choice is saved, so changing `DEFAULT_TONE` reverts everyone who never chose). Dark background near-black (#0B0E14-ish), panels one step lighter, 1px borders, no shadows/gradients.
- **Color is semantic only:** green = working/verified, amber = idle/waiting, red = loop/error/over-budget, blue = info/links, neutral gray for everything else. Brand accent (single hue, pick once at T7) used only for interactive elements. No decorative color anywhere — if a color doesn't encode state, it's gray.
- **Type:** UI in a neutral sans (Inter or system stack); **all numbers, costs, IDs, and terminal content in monospace with tabular numerals** — columns of costs must align.
- **Density:** compact rows, generous data-per-screen; sparklines over big charts on Now; big charts live on Cost/History only.
- **Motion:** none except live-data updates (value ticks, new-event flash ≤150ms). No spinners longer than 300ms — show last-known data with a staleness dot instead.

These tokens live in `ui/src/design/tokens.css` as the single source of truth; every component derives from them (same discipline Munder Difflin's DESIGN.md enforces, different taste).

## Narration map (T7)

The narration is a pure function `(tool_name, tool_input, recent history) → phrase`. Baseline phrases:

| Tool                     | Phrase                                      |
| ------------------------ | ------------------------------------------- |
| `Read`                   | reading `<basename>`                        |
| `Edit` / `Write`         | editing `<basename>` / writing `<basename>` |
| `Bash`                   | running `<first token(s) of command>`       |
| `Grep` / `Glob`          | searching for `<pattern>`                   |
| `WebFetch` / `WebSearch` | fetching `<host>` / searching the web       |
| `TodoWrite`              | planning — N/M done                         |
| `Task` / `Agent`         | delegating to a subagent                    |
| `mcp__<server>__<tool>`  | `<tool>` via `<server>`                     |
| unknown                  | using `<tool_name>`                         |

Repeats append an ordinal ("— 2nd attempt") when the same tool+input recurs; ≥ K repeats flip the health badge to `looping?`.
